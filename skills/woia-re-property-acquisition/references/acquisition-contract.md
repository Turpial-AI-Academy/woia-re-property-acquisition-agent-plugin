# Real Estate acquisition delta — ADR-0008

## Ownership and composition

This plugin specializes only the five published Supply Acquisition extension slots. The independently released generic base owns common acquisition method; Core owns Tasks, Due Work, requests/responses, Effect lifecycle, snapshots, selection and recovery. There is one selected specialized root; the generic base remains a dependency, not a second active root. The delta does not create a state store or Task engine.

Exact immutable Core v0.5.3 and Supply Acquisition v0.5.0 identities are in [release-bindings.json](release-bindings.json). Core main must never replace its release. The eight provider closure versions are semantic resource bindings, not eight package dependencies. RE Domain Contracts owns the canonical logical domain contract; none is copied here. Temporary coordinator documents are implementation provenance, never install/runtime dependencies.

The [delta-contract.json](delta-contract.json) records precisely five operations: SPECIALIZE service-intake, NARROW representation-authorization, SPECIALIZE readiness-evaluation, NARROW receiver-contribution, ADD outcome-continuity. Preserve base-conformance, authority-narrowing, provider-closure and update-recovery; additionally evaluate delta-semantics. In-flight snapshots remain pinned. Local tests are engineering evidence only. `NOT_QUALIFIED`, empty evaluated_pairs, activation denied remain in effect until the delta is finally released and exact immutable pair/provider evaluations pass through Core/Ecosystem's existing composition mechanism. This evaluator can never activate or qualify a pair.

## Five rules

1. Resolve actual sale, rental-placement or existing-lease-administration and exact shared Person/Organization principal + Property/unit scope. Combinations must be explicitly requested and host-authorized. Evaluate each service separately, with independent acceptance. Rental placement cannot activate administration; administration requires its own accepted active Lease and receiver transfer.
2. Distinguish ownership/right claim, representation/Mandate, evidence and competent authority. The independently resolved action policy and competent grant must bind organization, actor, property/unit, represented principal, purpose, service, scope version, next action and Source Authority Map revision. Check current interval, revocation, holds and emergency stop. Service-dependent action requires accepted current representation, Mandate and terms; dispute fails closed. Independently authorized unrelated read-only preparation may proceed without Mandate. No autonomous negotiation, valuation judgment or Offers.
3. Read accepted shared sources directly and require only evidence appropriate to the next action under the owner's accepted policy. Sale/rental offering requirements are organization-owned; no universal dossier. Existing-Lease administration requires the existing active Lease, participants, responsibilities, Documents and source/cutover context, not promotional photos, fictional Listing/tenant search/placement history. No monetary opening position is calculated or fabricated. Finance accepts financial/source consequences independently; Data owns source integrity, not rights acceptance.
4. Request only distinct receiver-owned outcomes through Core. Operations supplies required field/access/media evidence; Legal/Compliance competent controls; Customer Service permitted external clarification, scheduling and follow-up; Finance financial/source acceptance; Data governance/migration. Shared records, Knowledge and local playbooks are direct reads, not universal Data proxies. Communications or calendar, public/paid publication and finance writes are not executable by this delta. ACK, notification and even contribution completion do not mean accepted result or parent completion. Core response correlation must preserve receiver task != origin task and original scope/snapshot/action.
5. Report service/property/principal, accepted references, blockers, retained owner and next review. Sale offering intake is not sale/publication; rental intake is not application or Lease; administration delivery is not monetary settlement. Sales, Leasing or Asset Management independently accepts its exact transfer package. Acquisition stops owning accepted downstream operations, while other service scopes retain their own pending work. Changed source/scope/version requires reevaluation and new competent acceptance; immutable historical evidence remains. UNKNOWN means retain key and reconcile before retry, never infer failure/success or undo external effects. Recovery cannot rewrite downstream Tasks, revive revoked authority, or silently change a pinned Core snapshot.

## Pure helper trust boundary

`evaluateAcquisition(request, host, baseResult)` is an in-memory proposal/readiness evaluator. It has no provider adapter, persistence, dispatch or CLI accepting arbitrary authority JSON. The request schema is [acquisition-request.schema.json](acquisition-request.schema.json). `host` is separately supplied by the authenticated host after resolving accepted current organization action policies, Source Authority Map rules, grants, facts, contribution receipts and receiver acceptance records. A caller-provided `host`, ACCEPTED flag or decision string is not authentication. Installation, available tools and a plugin's helper output never grant authority. Real host/store/adapters and exact pair evaluation are later qualification gates.

`projectBaseInput(request, host)` only maps references to the published base's existing evaluateIntake API. Host must actually run that immutable base helper and pass its output; copying a PASS flag is invalid. Delta validates returned task, property subject, service, action, map revision and idempotency key. Original base input also binds organization, actor and purpose; host must never substitute results across contexts. Base checks remain independently necessary, never weakened by the delta.

Each host source rule and accepted fact binds scope/service/action/source map, trusted source, competent owner, immutable reference/version, accepted decision and current interval. Missing, duplicated, stale, disputed, revoked or noncompetently accepted inputs block. No inference becomes a fact.

Transfer requires a separately retrieved authoritative `transfer_acceptance`: current accepted receiver record with its immutable ref/version/source, competent accepted_by and `accepted_payload` equal to the proposed package. `transferPayload(request, host)` describes that package; it does not accept it. The package binds task, organization, actor, property/unit, principal, purpose, service, scope version, next action, source map revision, Core snapshot and all evidence kind/ref/version/source/decision tuples. Changing any source/version invalidates receiver acceptance. Notification and caller self-assertion are not accepted transfer. Host authenticates and verifies the receiver record/source; the helper checks exact correlation, not signatures or legal validity.

All outputs retain dispatch_performed/fact_written/authority_granted/task_written/pair_qualified/production_ready false and parent_completed false. `NEXT_ACTION_ELIGIBLE` means this one read-only engineering evaluation has no blockers; it is not permission to execute an external effect, activate a root or complete a Task.
